Mitigations verified by this run
--------------------------------

  1  brute force detection on the realm
     test: tentativas_repetidas_bloqueiam_a_conta
     after 40 wrong passwords the CORRECT password is refused, and the refusal
     is byte-identical to a wrong-password refusal, so the lockout adds no new
     oracle

  2  input validation
     tests: titulo_acima_do_limite_da_coluna_nao_pode_dar_500
            byte_nulo_no_titulo_nao_pode_dar_500
     both previously returned 500; both now return 400 with a generic body.
     The null-byte guard covers title AND body: Postgres rejects 0x00 in TEXT
     as well as in VARCHAR, so guarding only the title left the 500 reachable

  3  per-request logging
     tests: pedido_valido_fica_rastreavel, pedido_recusado_fica_rastreavel
     all seven required elements present for both a served and a refused
     request: date, time, source IP, route, method, HTTP status, caller id

Test bugs found while writing the suite
---------------------------------------

Kept because each is a lesson.

  1  Flipping the LAST character of a base64url signature can decode to the same
     bytes, so the "tampered signature" was identical to the real one and was
     accepted. The test now alters a middle character and asserts the decoded
     bytes differ.
  2  notes-reporter gets 403, not 404, on a single record: it holds
     app-notes-exporter but not app-user, so @PreAuthorize stops it before any
     record is in play.
  3  The leak scan flagged the suite's own SQL payloads, read back by a later
     test. Payload notes are now deleted immediately after being checked.
  4  A path such as /notes/all returns 400, which the expected set did not allow.
  5  After mitigation 3 the traceability tests still searched for the old
     NoteService line instead of the filter's.


Reproducing
-----------

  cd security-tests
  ./mint_tokens.sh /tmp/notes-api-seguranca.env
  set -a; . /tmp/notes-api-seguranca.env; set +a
  python3 -m unittest -v test_security

Three things make a run differ from the 45/38/7/0 above:

  - notes-web has direct_access_grants_enabled = false, by design. Without it
    there are no human tokens and six scenarios skip. They were run with the
    flag temporarily enabled, and it was turned off and verified afterwards.
  - The expired token must be past exp plus 60 seconds, because Spring
    Security's JwtTimestampValidator applies a 60-second clock skew by default.
    mint_tokens.sh caches one; a freshly minted one is only usable later.
  - Service tokens live 300 seconds. Minting and running must happen in one go:
    waiting in between produced one run with 31 false failures, all of them
    expired tokens.
